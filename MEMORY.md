## 1. Что это

Бот-ретранслятор для ручной переписки с клиентами.
Клиент пишет боту → сообщение попадает в приватную группу владельца, **один клиент = один топик форума** → владелец отвечает прямо в топике → бот доставляет ответ клиенту.

**Жёсткое требование заказчика: никакого AI, автоответов и генерации.** Отвечает только человек. Единственное автоматическое сообщение во всей системе — необязательный ответ на `/start` через `WELCOME_TEXT`, и он **выключен по умолчанию**. Есть тест, который это охраняет («бот НИЧЕГО не написал клиенту сам»).

## 2. История решения (важно для контекста)

Сначала была построена полноценная веб-панель оператора (React + PostgreSQL + SSE + роли + авторизация). Заказчик посмотрел и сказал, что это избыточно, и попросил **вариант попроще — ретрансляцию в группу с топиками**. Панель удалена целиком по его прямому указанию, репозиторий переписан с нуля. Возвращаться к ней не нужно, если он сам об этом не попросит.

Тогда же был проведён разбор ограничений Telegram, и он остаётся в силе:

- Bot API и MTProto — **две разные платформы**. Бот физически не может читать личные чаты вашего аккаунта.
- **MTProto/userbot (Telethon, GramJS) отвергнут**: серая зона ToS, риск бана номера, session string в БД = полный доступ к аккаунту.
- **Telegram Business Bots** (бот подключается к личному аккаунту, требует Premium у владельца) — рабочая альтернатива, если заказчик захочет, чтобы клиенты писали ему в личку, а не боту. Сейчас не используется.

## 3. Архитектура

Один Node-процесс. Хранилище — файл SQLite. Веб-интерфейса нет: рабочее место — обычный Telegram.

```
клиент (личный чат с ботом)
      │  update.message, chat.type === 'private'
      ▼
  handleUpdate → claimUpdate (дедуп по update_id)
      │
      ├─ upsertClient
      ├─ ensureTopic → createForumTopic + карточка клиента
      └─ copyMessage(→ группа, message_thread_id)

оператор (топик в группе)
      │  update.message, chat.id === GROUP_ID, message_thread_id
      ▼
  handleUpdate → фильтры (свой бот, служебные, //, команды)
      └─ copyMessage(→ личный чат клиента) + реакция 👌
```

### Ключевые решения

1. **`copyMessage` вместо разбора типов контента.** Один вызов переносит текст, фото, файлы, голосовые, кружки, стикеры. Не нужно писать ветки под каждый тип и скачивать файлы. Это главное упрощение проекта.
2. **Топики форума как модель диалогов.** Telegram сам даёт список чатов, поиск, непрочитанные и уведомления — их не надо реализовывать.
3. **Ноль runtime-зависимостей.** Node 22 даёт `fetch`, `node:sqlite`, `node:http`. `.env` читает свой загрузчик в 20 строк (`src/env.ts`). В `package.json` только devDependencies.
4. **Повторы внутри `call()` в `telegram.ts`**, а не отдельной очередью с воркером. Для такого объёма достаточно: 429 ждёт `retry_after`, 5xx и сетевые — экспоненциальный backoff, до 4 попыток. 400/401/403 не повторяются.
5. **Вебхук всегда отвечает 200**, даже при внутренней ошибке — иначе Telegram зациклит повторы и заблокирует очередь.
6. **Права = членство в группе.** Отдельной авторизации нет; кто в группе, тот и оператор. Осознанный размен на простоту, записан в README как ограничение.
7. **HTTP-сервер (`server.ts`) запускается всегда**, независимо от `MODE` (polling/webhook) — с добавлением приёма заявок с сайта (`/leads`) появился второй, не связанный с Telegram-режимом публичный вход, которому нужен порт вне зависимости от того, как бот получает апдейты. Раньше сервер поднимался только при `MODE=webhook` — это изменилось при добавлении фичи заявок (см. п.11 ниже).

## 4. Обнаруженные ограничения Telegram

- **Group Privacy у бота должен быть выключен** (@BotFather → Bot Settings → Group Privacy → Turn off), иначе бот не видит обычные сообщения в группе и ответы оператора никуда не уйдут. Через API это не проверить — только предупреждение в `npm run setup`. После смены настройки бота надо **удалить из группы и добавить заново**.
- Темы (Topics) есть только у **супергрупп**. Обычная группа становится супергруппой после добавления второго участника.
- Боту нужно право **«Управление темами»**, иначе `createForumTopic` вернёт ошибку.
- Сообщения в топике **General** приходят без `message_thread_id` — к клиенту не привязаны, игнорируются.
- Свои же скопированные сообщения бот получает обратно как апдейты. Без фильтра `from.id === botId` получилось бы зацикливание.
- Удалённый вручную топик даёт `message thread not found` → пересоздаём и повторяем один раз.
- Закрытый топик даёт `TOPIC_CLOSED` → переоткрываем и повторяем.
- Лимиты: ~1 сообщение/сек в один чат, ~20/мин в группу. Реализован троттлинг по chat_id в `telegram.ts`.
- Telegram не гарантирует ровно-однократную доставку вебхука → дедуп по `update_id` в таблице `seen_updates`.
- `getUpdates` и webhook взаимоисключающи (409). Poller сам снимает вебхук при старте.
- Номер телефона клиента приходит, **только если он сам поделился контактом**.
- Альбом из нескольких фото приходит отдельными апдейтами — в топике будет несколько сообщений.

## 6. Схема хранилища

```sql
clients (
  user_id PK, thread_id UNIQUE, first_name, last_name, username,
  language_code, phone, first_seen_at, last_seen_at, banned
)
seen_updates (update_id PK, at)   -- дедупликация, чистится раз в 6 часов
state (k PK, v)                   -- offset для polling
```

Файл: `data/relay.db` (путь в `DB_FILE`). **Требует постоянного диска в production** — если потерять, привязка клиентов к топикам исчезнет и всем создадутся новые топики.

## 12. Грабли

- **Group Privacy** — причина №1, по которой «бот не отвечает». Проверяется только глазами.
- Без фильтра `from.id === botId` бот зацикливается на собственных копиях.
- В Git Bash на Windows кириллица в аргументах `curl` ломается кодировкой — тестовые данные слать только из Node-скриптов.
- В тестах заголовки HTTP не принимают не-ASCII: секреты только латиницей.
- `node:sqlite` синхронный и помечен экспериментальным — при старте Node печатает `ExperimentalWarning`. Это нормально.
- Фоновые процессы, запущенные через Bash-тул, умирают вместе с шеллом; для ручных проверок запускать через `nohup` или отдельным окном.
- В PowerShell (Windows) `&&` работает только в новых версиях; в старой Windows PowerShell 5.1 команды нужно выполнять по отдельности.
- После добавления `/leads` HTTP-сервер стал нужен всегда (см. решение №7 в разделе 3) — если в будущем добавится ещё один HTTP-вход, добавлять его тоже в `server.ts`, а не создавать третий отдельный сервер/порт.
- **Oracle Console UI разошёлся с текстом DEPLOY.md** в паре мест (интерфейс меняется со временем): кнопка скачивания ключа называется «Download private key», а не «Save private key»; при первом создании VM образ по умолчанию — Oracle Linux, Ubuntu нужно выбрать вручную через «Change image»; сети (VCN) при первом инстансе ещё нет — нужно выбрать «Create new virtual cloud network», а не «Select existing»; свежесозданный инстанс может не получить Public IP автоматически — назначается вручную через Instance access → «ephemeral public IP» (не «reserved», та ссылка ведёт в документацию, а не в форму назначения) → либо через Networking → VNIC → **IP administration** → Edit у приватного IP. - **Шаблон `deploy/telegram-relay-bot.service` содержит захардкоженный путь `/home/ubuntu/telegram-relay-bot`.** Если репозиторий клонирован под другим именем (у нас — `finfix-bot`, по имени репозитория на GitHub) — служба падает с `Failed to load environment files: No such file or directory` / `Result: resources`. Стоит поправить сам файл в репозитории, чтобы путь не был захардкожен — либо генерировать юнит скриптом, подставляя реальный `$(pwd)`.
- **Настоящая причина, по которой открытый в ufw порт всё равно не был доступен снаружи**: у образа Ubuntu на Oracle **заранее прописаны iptables-правила** (видимо, часть базового образа) — INPUT-цепочка вида `ACCEPT NEW tcp dpt:22` → `REJECT всё остальное` → и только **после** этого REJECT идут цепочки `ufw-*`. То есть пакеты на любой порт, кроме 22, отклоняются ДО того, как их вообще увидит ufw — сам ufw в такой ситуации совершенно бессилен, сколько бы правил в нём ни добавляй. Диагностика: `sudo iptables -L INPUT -n --line-numbers -v` — если REJECT стоит раньше `ufw-before-input` и других `ufw-*` цепочек, вот она, причина. Фикс: `sudo iptables -I INPUT <номер_перед_REJECT> -m state --state NEW -p tcp --dport <порт> -j ACCEPT`, затем `sudo netfilter-persistent save` (доустановить `iptables-persistent`, если нет). Это стоит внести в DEPLOY.md шаг C3.1 как основную причину проблемы, а не только Security List — Security List на практике не был причиной, всё упиралось именно в этот преднастроенный iptables.
- **Право «Управление темами» боту нужно выдавать отдельно** — то, что бот назначен администратором группы, само по себе это право не включает. Без него `createForumTopic` падает с `Bad Request: not enough rights to create a topic`. Чинится: Группа → Администраторы → бот → включить «Manage Topics» отдельным тумблером.
- **В Telegram-группе есть тема General по умолчанию, и туда же изначально падают тестовые сообщения**, если писать прямо в группу (не боту в личку) — это ожидаемо, `GROUP_ID` в логе появляется именно из таких сообщений в General, когда бот ещё не знает, что это его рабочая группа.
- Периодические `NetworkError: fetch failed` во время long-polling на Oracle — судя по всему, особенность сетевой инфраструктуры Oracle (рвёт подолгу висящие соединения раньше 25-35 сек таймаута). На доставку сообщений не влияет (retry в `poller.ts` сам восстанавливается), но шумит в логе. Не исправлено — можно смягчить, уменьшив `timeout` в `getUpdates`, если будет мешать.
- **«Free Trial» и «Always Free» в Oracle — разные вещи**, баннер про истечение триала пугает раньше времени. Наш `E2.1.Micro` помечен «Always Free-eligible» и продолжит работать бесплатно и после 30 дней триала — предупреждение относится к бонусным кредитам на платные ресурсы, которых мы не касались.
